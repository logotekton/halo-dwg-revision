# 사용자 리비전 쌍 (`samples/revision-pairs/`)

R1 게이트의 `owner-pair` 확인(`docs/gates/R1.md`)에 쓰는, 사용자가 직접 만든 변경 전·후 DWG
세트다. `samples/`는 통째로 `.gitignore`(`/samples/`)에 걸려 있어 안의 DWG는 저장소에 들어오지
않는다 — 이 `README.md`만 `git add -f`로 예외로 추적한다(원본 도면·프로젝트 산출물은 절대 커밋
하지 않는다, `CLAUDE.md` 절대 규칙 1).

## 폴더 규약

```
samples/revision-pairs/
└── <이름>/
    ├── before/          # 변경 전 DWG/DXF (원본 그대로, 이 폴더 자체를 수정하지 않는다)
    ├── after/           # 변경 후 DWG/DXF (before를 복사해 실제로 손을 댄 결과)
    └── planted.md       # 심은 변경 목록 (아래 형식)
```

- `<이름>`은 자유롭게 정한다(예: `owner-pair-01`, `2026-09-04-전기`). 여러 쌍을 만들면 폴더를
  여러 개 둔다 — `docs/gates/R1.md`의 "클러스터(owner-pair)" 표를 쌍마다 하나씩 채운다.
  파일 이름(도면번호)이 겹치는 여러 시트를 한 쌍에 넣어도 된다(도곽 단위로 비교하므로 파일
  하나에 시트가 여러 장이어도 무방하다, `docs/dev/compare-frames.md`).
- `before/`와 `after/`는 앱이 요구하는 만큼만 있으면 된다 — 안 바뀐 시트를 포함해도 되고
  ("동일" 상태로 나온다), 심은 변경이 있는 시트만 넣어도 된다.
- 이 폴더 전체가 **사용자가 직접** 화면 A에서 "폴더 선택…"으로 지정하는 대상이다. 앱이 여기에
  쓰는 것은 `.halo/`(비교 번들)와 `<프로젝트>/출력/<날짜>/`뿐이고, `before/`·`after/` 원본은
  절대 열어 쓰지 않는다(`CLAUDE.md` 절대 규칙 1 — 게이트 확인 항목 `원본-불변-win`이 이걸 본다).

## `planted.md` 형식

한 쌍(폴더 하나)에 심은 변경을 도곽(도면번호) 단위로 적는다. 표 형식을 권장하지만 자유
서술이어도 된다 — 앱이 이 파일을 읽는 것은 아니고, 사람이 화면 C에서 승인·무시할 때와 게이트
결과를 채점할 때 대조하는 답안지다.

```markdown
# 리비전 쌍: <이름>

만든 날짜: 2026-09-04
공종/출처 도면: (예: 01_건축, samples/2026-09-02-실시도서/에서 복사해 만듦)

## 심은 변경

| 도면번호 | 위치/부근 | 심은 변경 종류 | 기대 클러스터 수 | 비고 |
|---|---|---|---:|---|
| A-101 | 1층 거실 남쪽 벽 | added (벽 신설) | 1 | 폭 900 벽 하나 추가 |
| A-101 | 1층 현관 문 D2 | moved (문 이동) | 1 | 동쪽으로 1,200mm |
| A-102 | 2층 평면도 치수선 | dimension (치수값 변경) | 1 | 12,000 → 12,500 |
| A-102 | 2층 실명 텍스트 | text (문구 변경) | 1 | "거실" → "리빙룸" |
| A-103 | (전체) | 변경 없음 | 0 | 대조군 — 아무것도 안 건드림 |

## 기대 총합

- 기대 클러스터 총합: 4
- 심지 않은 도곽(A-103 등)의 기대 클러스터: 0
```

"심은 변경 종류"는 엔진의 `change.kind`(`docs/seeds/R1-mvp-2026-09-04.yaml`의 `ontology_schema`,
`apps/web/src/i18n/ko.json`의 `compare.review.kind`)와 같은 어휘를 쓰면 화면 C의 자동 문구와
바로 대조할 수 있다: `added`(신설)·`removed`(삭제)·`modified`(수정)·`moved`(이동)·`text`(문구)·
`dimension`(치수)·`blockdef`(블록 정의)·`mixed`(혼합). 이동을 심을 때는 0.01mm보다 뚜렷하게
움직여야 한다 — 그 이하는 "사소한 변경"으로 접혀 클러스터가 되지 않는다(`compare.yaml`
`minor.move_tolerance`, `CLAUDE.md` 절대 규칙 7).

"기대 클러스터 수"는 개별 변경 수가 아니라 화면 C에 뜰 **클라우드 마크 개수**다 — 가까운 변경
여럿은 하나의 클러스터로 묶인다(`docs/dev/compare-engine.md` "클러스터와 번호", 묶는 거리는
도곽 크기와 축척에 따라 달라진다). 여러 변경을 일부러 멀리 떨어뜨려 심으면 클러스터 수를
예측하기 쉽다.

## 확인 절차와의 관계

`docs/gates/R1.md`의 "사용자 확인" 절차 5단계(리비전 쌍 지정)·7단계(화면 C 승인·무시)가 이
폴더를 그대로 쓴다. `owner-pair` 게이트는 다음 둘을 모두 만족해야 PASS다.

- 이 파일에 적은 심은 변경이 **전부** 클러스터로 나온다(기대 클러스터 수와 화면 C에서 실제로
  본 클러스터 수가 일치).
- 심지 않은 자리(대조군 도곽 포함)에는 클러스터가 **하나도** 없다(오탐 0).

쌍이 아직 없으면 `docs/gates/R1.md`의 `owner-pair` 항목은 "쌍 제공 후 수행"으로 두고 `R1-GATE
owner-pair: (대기)`로 남긴다 — 합성 쌍(`fixtures/compare/S*`)만으로는 이 게이트를 닫을 수 없다
(Seed acceptance_criteria가 "사용자 리비전 쌍"을 명시한다).
